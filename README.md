# QuantumTeam

## Кривые и расчётные бакеты

Кривая для графика и экспорта содержит 19 фактических сроков до **30 лет**.
База и стрессовый шок рассчитываются на одном и том же сроке.
`GET /api/v1/curves/{id}/term-structure?scenario=base` возвращает базу;
вместо `base` можно передать код сценария, например `steepener`.

Расчёт NPV и сверка с Excel используют отдельные 19 бакетов и их середины
(последняя — **25 лет**). Эти сроки не заменяются на сроки кривой.
`GET /api/v1/curves/{id}/base` и `/scenarios/{scenario_id}` возвращают бакетные значения.

Экспорт `/api/v1/exports/curves/{id}/moex.csv` содержит
`trade_date,scenario,tenor_years,rate`, сроки до 30 лет, ставку в долях единицы.
Старый бакетный формат с `bucket_code` доступен по `/buckets.csv`.
Демонстрационный экспорт `/calculator-demo.csv` по-прежнему является заглушкой.

## История расчётов и обновление существующей БД

Каждый импорт создаёт снимок с новым ID, даже за ту же торговую дату.
Пересчёт через `/api/v1/curves/{id}/rebuild` создаёт новую версию; результат RQ
содержит `snapshot_id` новой версии и `original_snapshot_id` исходной.
Готовые и неудачные версии повторно не записываются. Статус новой версии
меняется из `pending` в `built` или `failed`; параметры старых снимков не меняются.
Все точки нового расчёта сохраняются одной транзакцией.

`GET /api/v1/curves/history?limit=100&offset=0` показывает историю версий.
`/latest` выбирает последнюю успешную версию наиболее поздней торговой даты.
Старые точки доступны по прежним ID; новые term-кривые появляются только
после нового расчёта. Автоматически достраивать и менять старые результаты не нужно.

При запуске `init_db()` автоматически выполняется идемпотентная миграция
PostgreSQL из `src/db/migrations.py`: снимается уникальность даты/источника,
каскадное удаление заменяется на RESTRICT, добавляется таблица term-кривых.
Таблицы и записи не удаляются. Миграция выполняется в транзакции под advisory lock.
Старая SQLite-схема не мигрируется: SQLite используется только в тестах с новой схемой.

Для обновления уже запущенной системы остановите API, Airflow и воркер,
чтобы старый код не выполнял пересчёт во время перехода, затем запустите:

```powershell
docker compose stop api airflow rq-worker
docker compose up -d --build
```

Перед обновлением рабочей БД сохраните резервную копию. **Не используйте
`docker compose down -v`: эта команда удаляет данные.**

## Время

Соединения PostgreSQL и API используют UTC, `fetched_at` содержит часовой пояс.
Интерфейс явно переводит время создания версии в **Europe/Moscow (МСК, UTC+3)**,
независимо от часового пояса браузера. Торговая дата MOEX остаётся датой.
Airflow запускает DAG по будням в **06:00 Europe/Moscow**; в Compose явно
заданы часовые пояса планировщика и его интерфейса.

## Тесты

```powershell
$env:PYTHONPATH="src"
py -m unittest discover -s tests -v
```

Тесты работают на временной SQLite и подменяют ответы MOEX; рабочая БД
не используется. SQL миграции PostgreSQL проверяется отдельно без выполнения
на реальном сервере — перед рабочим обновлением нужно проверить её на копии БД.
